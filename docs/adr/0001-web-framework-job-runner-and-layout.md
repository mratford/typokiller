# Web framework, job runner and project layout

The spec (#17, §2) left three choices to the first build ticket (#18). typokiller has one user on a LAN, so each choice takes the simplest option that will still work when later tickets add Lessons, imports and charts.

## Web framework: FastAPI on uvicorn

FastAPI checks the shape of each batch of key events with Pydantic models, and its test client lets tests call the API without a running server. The page is plain JavaScript served as static files by the same app, so there is no build step. The database is the standard `sqlite3` module with SQL written by hand; there is no ORM. Endpoints are `async`, so all database work runs on one thread and no locking is needed.

## Job runner: tasks inside the server process

Background work (Lesson generation, git clones, the Gutenberg catalogue refresh) runs as `asyncio` tasks in the server process. Lesson generation will read from an `asyncio.Queue` so that requests wait in order. Blocking work runs through `asyncio.to_thread`. There is no separate worker process and no Redis. #21 added the first background work, the Gutenberg catalogue refresh: one task started with the app that checks every hour, so it needs no queue. #22 added git clones without a queue too: each request starts its own task, so several clones can run at the same time.

## Project layout

- `pyproject.toml`, managed with `uv`. `uv run typokiller` starts the server on port 8000 on all interfaces.
- `src/typokiller/app.py`: the schema, the API, the static file mount, the downloads from gutenberg.org with the catalogue refresh, and the git clones.
- `src/typokiller/keymap.py`: reads the QMK settings and the Letter layout from a `.vil` and a `vial.json`, and finds which keys of a `.vil` type each character.
- `src/typokiller/sources.py`: the `ascii-v1` normaliser, splitting a Gutenberg book or a code file into Passages, and searching the Gutenberg catalogue.
- `src/typokiller/analysis.py`: the tables computed on read with Polars, and the progress page's numbers and its Altair chart, used by the app and the notebooks.
- `src/typokiller/drills.py`: the Drill generators and the word pool that Drills take their words from.
- `src/typokiller/lessons.py`: the interface that each model provider must have (`Provider`), the Lesson prompts, the spend ledger's cap, and running a Lesson's code blocks under `sandbox-exec` (`run_code`, `RUNNERS`). The OpenRouter provider is in `app.py` with the other downloads.
- `src/typokiller/gleam/`: the pre-made Gleam project that Gleam code blocks are built in (#33). Its `gleam.toml` and `manifest.toml` are in git; its `build/` folder is not.
- `src/typokiller/drawing.py`: `draw_keymap`, which draws one layer of a Keymap as SVG for the app and the notebooks.
- `src/typokiller/static/`: the page. `typing.js` holds the typing rules and has no DOM code, so Node can test it. `progress.js` is the progress page.
- `tests/`: `pytest` for the API, `node --test` for `typing.js`.
- The database is `typokiller.db` in the working directory. The settings file is `typokiller.toml` next to it; it is created with defaults and comments when it is missing.

## Consequences

- The schema is created with `CREATE TABLE IF NOT EXISTS`. A later ticket that changes a table has to add its own `ALTER TABLE`. #19 added `attempt.settings` and #20 added `session.keymap_version` this way; rows stored before then have NULL there.
- A Board stores its `vial.json` and has one row in `keymap_version` for each distinct `.vil`, keyed by a hash of the file. A Keymap is not stored: it is a Board with one Letter layout, and its versions are the `.vil` files of that Board with that Letter layout. A new Session uses the newest version. Adding a Board with a name that exists adds the `.vil` to that Board and replaces its `vial.json`. The Letter layout is computed on read, so a `.vil` that changes its letters starts a new Keymap.
- A Session has no stored end time. It is computed when the data is read, as `started` plus the `t` of the Session's last key event. `t` counts from page load, which is a little before `started`, so the result is a little late. A stored end time was tried, but it could not be sent reliably when the tab closes. The spec (§5) lists "end" on Session; this is the change.
- The browser keeps key events until the server confirms it has stored them, and sends them again until then. The server ignores events it already has, so batches may overlap. The last batch before the page closes is sent with `keepalive`, which Chrome limits to 64 KB, so only that batch uses it.
- The server stores an Attempt when it receives the Attempt's first key event. The Attempt stays abandoned unless the page reports it as finished. So an Attempt with no key events, such as a restart before typing anything, is not stored.
- #21 added the `source` and `passage` tables and `attempt.passage`. The `PASSAGE` text in `app.py` is Passage 1, which has no Source. It is typed when no Source is open, and every Attempt stored before #21 is linked to it.
- A Source's bookmark is the ord of its next Passage. Paragraphs skipped because of the `[passages]` settings (`max_dropped`, `min_length`) are not stored as Passages, so the ords have no gaps. A Source stores its number of Passages as `total`, and it is finished when its bookmark equals `total`. The last used Source is the one with the latest `opened` time; setting the bookmark updates it.
- The server serves a Passage together with the one after it. After a Source's last Passage, the built-in Passage comes next, so the page always has a next Passage to show at once.
- The Gutenberg catalogue is `pg_catalog.csv` next to the database. It is downloaded when it is missing or a week old, and read again for each search. Downloads use the `truststore` package so that certificates are checked with the macOS keychain: Python's default certificate file lacks the root certificate that gutenberg.org uses.
- The page reads the settings file when an Attempt starts and sends those settings with the Attempt's key events. Attempt stores them as JSON in its `settings` column, so the wrong-key mode is `settings ->> '$.typing.wrong_key_mode'`; there is no separate column for it. Attempts stored before #19 have no settings; they were all typed in "keep typing" mode.
- Whether the Keymap was drawn under the Passage (spec §5) is the setting `typing.show_keymap`, so each Attempt stores it in its `settings` column like the wrong-key mode: `settings ->> '$.typing.show_keymap'`. Attempts from before #28 have no value there; the Keymap was not shown for them. `m` changes the setting in the file and in the current Attempt at once. The server stores an Attempt's settings with its first batch of key events, so an Attempt where `m` was pressed after that records the value it started with.
- #22 added code Sources. `POST /api/code` clones the repo with `git clone --depth 1` in a temporary folder, in an `asyncio` task of its own, and returns at once. There is no queue, so clones may run at the same time. The task keeps only the text files that git tracks (valid UTF-8 with no NUL character, not symbolic links), shuffles them once, and splits each file into functions at blank lines. A code Source stores its text as each file's text after a `--- path` line, in the shuffled order; its Passages have the same order. `ascii-v1` keeps `\n`, so code Passages have newlines; prose Passages have none because their line breaks become spaces before normalising.
- Background work reports to the page through notices: `GET /api/notices` returns a list of strings that the server keeps in memory, so it is empty again after a restart. The page reads it every second and shows each notice added since the page loaded on the message line. Later background work (the article bookmarklet, Lessons) appends its notices to the same list.
- #23 added articles. The bookmarklet opens `/send#<JSON {title, text}>` in a new window; that page posts the JSON to `POST /api/articles` and closes itself. `GET /send` is a route of its own, because `StaticFiles` serves the page only as `/send.html`. The Source text is the text exactly as sent. Each non-empty line is a paragraph (`innerText` puts each block of the page on its own line), a line that is there more than once is dropped, and the rest goes through the prose skip rule. An article with no Passage left is refused with 422 and not stored. (A book or repo with no Passages is still stored.) The page URL is not stored.
- Code typing rules (#22, in `typing.js`): Enter goes in only where the Passage has `\n`. The spaces at the start of the next line are then added to the typed text with no key events. Backspace just after those spaces removes them together with the newline. Code that replays key events to find what was typed must follow these rules. Tabs in code become 4 columns when the Passage is made, so a file written for 8-column tabs looks different from the file.
- #24 added `analysis.py` and Polars. Its tables are computed on read from the key events, and sorted on explicit columns. A cache in memory was added later (see the last item). `since` keeps only the Sessions started at that time or later; an Attempt's time is its Session's start.
  - `keydowns(db, since)` replays each Attempt's keydowns with `apply_key`, a Python copy of `applyKey` in `typing.js`. It lines them up with the Passage by `first_error_v1`. There is one row per keydown, with its position, its status (correct, error, off-track or ignored), whether it is the first keystroke at that position, and an Error's fix time.
  - `attempts(db, since)` has one row per Attempt, with WPM and first-time accuracy.
  - `GET /api/sessions/{session}/attempts/{ord}/summary` returns the Attempt's WPM and accuracy. It also returns the medians over the finished Attempts of the last 4 weeks on the same Board and Letter layout. The page asks for it after the finished Attempt's last keyup and a flush, so the server has all its key events.
- #25 added key attribution and the `keystrokes` table, both computed on read.
  - `read_keymap(vil)` (cached) follows each keycode of a `.vil` to the character it types under the Australian input source. `keys[char]` lists the keys that type a character: first the keys that type it alone, then the keys that type it with Shift held (capitals, Caps Word, the Shift + `_` key override); each group by layer, then matrix position. A key is a `Key(layer, key, kind)`: `key` is the matrix position `"row,col"` as `vial.json` labels it, or for a combo its keys joined by `+`; `kind` is plain, mod-tap, layer-tap, combo or macro. `KC_TRNS` keys are skipped. Combos are on layer 0. Only the keycodes in the sweep-layouts `.vil` files are known; other keycodes type nothing.
  - `keystrokes(db, since)` has one row per keydown that `keydowns` gives a position, plus one row per combo misfire. The picked key is the first candidate on the layer of the Passage character's own first candidate, or else the first candidate; for a correct key, that is the first candidate. `event` is `typed`, `mod-tap misfire`, `combo misfire` or `macro misfire`; misfire rows have no first-time-correct value and no timing. Macro text is found as a burst of the macro's text with keydowns at most 5 ms apart.
  - Keyups pair with keydowns by `code`. `dwell` is None for mod-taps and layer-taps (also when a quick re-tap kept a real dwell), for lost keyups, and for keys that are not finger presses (macros, combo outputs, auto-repeat, off-track keys). `flight` runs from the previous keystroke's keyup to this keydown, when only modifier keys came between. Around a run of mod-tap or layer-tap keys, every pair gets the time from the keyup before the run to the keydown after it.
  - `first_error_v1` rows, and so the `keydowns` table, now also have `cursor`: the number of characters typed before the key. Combo misfires use it as their position.
- #26 added the Weakness model, computed on read like the other tables.
  - `keystrokes` has a `time` column: from the previous keystroke's keydown to this keydown, where the keystroke has a flight. Around a run of mod-tap or layer-tap keys, whose keydowns come at their release, every pair in the run gets an equal share of the time from the keydown before the run to the keydown after it. The spec (§3) says to score these pairs by the summed time; this is the change, because a summed time puts each such pair at about twice the cost of a plain pair. `flight` still gives the summed time.
  - `WEAKNESS_MODELS` in `analysis.py` holds each Weakness model by name, with its colour scale for drawings (low, high and tick costs in ms). `weakness(db, board, letter_layout, settings)` runs the model named in the `[weakness]` settings table and returns its ranking, the highest cost first, with a `model` column. The `[weakness]` table holds `model` (default `recent-cost-v1`), `weeks` (4) and `min_seen` (20). The Attempt summary medians use the same `weeks`.
  - `recent-cost-v1`: for each character and pair (the character before and this one, when the keystroke before was correct), cost (ms) = median `time` of its correct keystrokes + error rate × median fix time of its Errors. The error rate and `seen` count only the first keystrokes at a position. Misfires and off-track keys do not count; abandoned Attempts do. Units seen fewer than `min_seen` times, or never timed, are left out. Its scale is 150–600 ms with a tick at 400.
  - The Attempt summary's slowest pairs are the pairs of the Attempt's Passage that the ranking holds, the 3 highest. With fewer than `min_seen` observations there are none, and the page leaves the part out.
- #27 added Drills, in the new module `drills.py`.
  - A Drill is a row of `passage` with no Source. It also has a row in the new `drill` table. That row holds the Passage, the time it was made, and the Session it was made for, which gives the Board and Letter layout. It also holds the names of the Weakness model and the Drill generator, and the Targets as JSON.
  - Each Target has a unit, a reason ("weak" or "under-measured"), a cost and a seen count. The cost is NULL when the Weakness model does not rank the unit.
  - `drill.unlocked` is NULL when the Drill could use every key. #30 stores the Unlocked keys there on a Letter layout being learned.
  - `POST /api/sessions/{session}/drills` makes a Drill and returns its id, text and Targets. It uses the generator named in the new `[drills]` settings table. That table holds `generator`, `weak`, `under_measured`, `min_seen` and `words`.
  - `DRILL_GENERATORS` holds each generator by name. A generator takes the database, the Board, the Letter layout, all the settings and the Unlocked keys (None for every key). It returns the Targets and the text.
  - `density-v1` takes the 2 units that the Weakness model ranks highest. Then it takes the most common units of the word pool that were seen fewer than `min_seen` times on this Board and Letter layout, in the Weakness model's `weeks`.
  - The seen counts come from `analysis.units`, the step that `recent-cost-v1` also uses. They do not come from the ranking, because the ranking leaves out units that were never timed.
  - A Target must be a unit that the pool's words hold, so `\n` is never a Target. Word i holds Target i modulo 3. It is picked at random, with a weight of its number of Targets per character.
  - The word pool is every whitespace-separated word of the Sources' Passages, with how often it comes. `WORDS` (500 common English words) joins it while the Sources give fewer than 1,000 different words. The pool is read again for each Drill. There is no cache.
  - Making a Drill reads the `units` table twice: once for the seen counts, and once in the Weakness model. With the analysis cache (see the last item), the key events are replayed only once.
  - On the page, `d` makes one Drill. After it, the interrupted Passage comes back from its start. `d` during a Drill makes another Drill that comes back to the same Passage.
  - The last item of the `o` list is endless Drills. After each Drill, the page sends its key events and asks for the next Drill, so the Targets are ranked again with that Drill's keys. The screen says "Making a Drill…" meanwhile, and no key does anything until the Drill comes. Choosing a Source ends the Drills.
  - The status line shows "drill" as the mode, and the Targets.
- The analysis cache. Replaying 4 weeks of key events took about 5 s for the Attempt summary and 8 s for a Drill at 250k keystrokes, and the server answers no other request meanwhile. So `analysis.py` now keeps what replaying each Attempt gives, in memory: its rows of `keydowns` and `keystrokes`, its WPM time and its accuracy. The raw key events are still the only stored data; there is no new table.
  - The cache is a dict in `analysis.py` (`replay_cache`), keyed by (database file, session, ord). Each entry keeps the Attempt's number of key events. On each call, one query counts the key events of each Attempt in the Sessions that the call asks for, and an Attempt whose count changed (a late keyup, a batch sent again) is replayed again. Everything else that the rows depend on is stored once and never changes: the Attempt's Passage and settings, and its Session's Keymap version. The Board name and Letter layout are joined on after the cache, so a replaced `vial.json` still shows.
  - Code that changes an Attempt's stored rows in some other way (for example a hand-made `UPDATE` of `key_event`, or a change to the replay code in a running notebook) must clear `analysis.replay_cache`.
  - In-memory databases are not cached. The notebooks call the same functions on their own connection, and get a cache of their own in their own process.
  - The index `key_event_attempt` on `key_event (session, attempt)` makes the count query fast.
  - Entries are never removed. An Attempt older than 4 weeks stays in memory until the server stops.
  - The first call after the server starts replays the last 4 weeks: about 3.3 s at 250k keystrokes. After that, the summary takes about 0.2 s and a Drill about 0.3 s.
- #28 added Keymap drawings, in the new module `drawing.py`.
  - `draw_keymap(vil, vial, layer, names)` returns an SVG of one layer, from the texts of the `.vil` and the `vial.json`. Key positions come from the `vial.json` KLE layout (`key_places`), with rotation; encoders, decals and layout options other than the first choice are not drawn. With no `vial.json` (`None`), the matrix is drawn as a plain grid. Each key is a `<g>` with the id `k<row>,<col>`, and a combo `k` and its keys joined by `+`, the same as the `key` column of `keystrokes`. The SVG holds its own `<style>`, which uses the page's colour variables with defaults for a notebook. #29 added the Weakness heat and #30 the unlock state, as classes and fills in the loop over keys.
  - Layer names come from the new `[keymaps]` settings table: `[keymaps.<Board>.<Letter layout>]` with `layers = [...]`. A layer with no name is called by the tap legend of the base-layer key that opens it (`LT(1,KC_SPC)` gives "Space"), else `L<n>`.
  - `GET /api/sessions/{session}/keymap` returns `{layers: [svg, ...], keys: {char: {layer, key}}}`: a drawing of each layer up to the last one that is not empty, and each character's first candidate, which key attribution picks for a correct keystroke. The page fetches it once when the Session starts. While typing, it shows the layer of the next character, and adds the class `next` to the key to press, which outlines it.
  - The settings page now sends only the value that changed, so `PUT /api/settings` no longer rewrites the other tables. It shows values of a table inside a table, such as layer names, but they are edited in the file.
  - `read_settings` now also adds a setting that is missing from a table of an older file, such as `typing.show_keymap`, with its default value but without its comment. Before, only whole missing tables were added.
- #29 added the progress page and Altair.
  - `analysis.progress(db, board, letter_layout, settings)` gives what the page shows, so a notebook can show the same: the trend (one row per day with a finished Attempt in the last 13 weeks, `TREND_WEEKS`: the medians of that day's WPM and first-time accuracy, and the number of Attempts), the 10 weakest characters and pairs of the Weakness ranking, and a `Heat` record (the ranking's costs, every unit's seen count from `analysis.seen_counts`, and the model's colour scale). A day is the date of the Session start in the Mac's time zone. `analysis.trend_chart(trend)` is the Altair chart; the server sends it as a Vega-Lite spec with the data in it.
  - The first call after the server starts replays 13 weeks of key events, not 4: about 2.8 s at 180k keystrokes. After that it takes about 0.15 s.
  - `draw_keymap(..., heat, pairs)` colours each key: the top half by the Shifted character's cost, the bottom half by the unshifted one's, each with its ms. A key with no Shifted character is one colour. A half that the Weakness model does not rank (seen fewer than `min_seen` times, or never timed) is hatched and shows `n=<seen>`. Keys that type no character, macros and combos are grey. The colours are a fixed ramp over the model's scale, the same in dark mode, with a legend under the keys that marks the tick. Each pair is a `<g class="arc" data-pair="...">` from the first character's first candidate key to the second's; the page hides all but the selected one.
  - `GET /api/keymaps/{version}/progress` returns `{weeks, days, trend, names, layers, chars, pairs}` for the Board and Letter layout of a Keymap version. The page lists the Keymaps from `GET /api/boards`.
  - The page is its own element, `#progress`, next to `#app`, so the chart is drawn once when its data comes, not on each key. `vega`, `vega-lite` and `vega-embed` are loaded from cdn.jsdelivr.net with exact versions the first time the page opens, so the practice screen never waits for the internet. `vega-lite` is the version of Altair's schema (6.4.1); a new Altair may need a new version there.
- #30 added free-range unlocking.
  - The `[unlocking]` settings table names the one Letter layout being learned (`letter_layout`, default free-range), its starting set and unlock order (each key written as the character it types without Shift), and the rule's `threshold`, `last` and `min_seen`. Other Letter layouts have no locked keys.
  - The new table `unlock` is the unlock log: one row per unlock with the Letter layout, the key, the time, `how` ("rule" or "manual"), the `[unlocking]` settings as JSON, and the Weakness model. Unlocked keys = the starting set + the log, in that order. Rows are never deleted.
  - A Weakness model's `rank` now takes rows of `units` and the `[weakness]` settings, not the database. `weakness()` gives it the last `weeks` weeks of one Board × Letter layout, as before. The unlock rule gives it each Unlocked character's last `last` rows of `analysis.layout_units` (every Board with the Letter layout, all time), with `min_seen` from `[unlocking]`.
  - The rule runs in `POST /api/sessions/{session}/batch` when the batch finishes an Attempt: at most one key per batch. It costs about 0.2 s at 360k key events. `POST /api/sessions/{session}/unlocks` (`u`) unlocks by hand and returns the state; 409 when nothing can unlock. Each unlock adds a notice.
  - Introduction Drills are due while the newest key of the log has been seen fewer than `min_seen` times since its unlock, on every Board with the Letter layout. A keystroke's time for this is its Session's start plus its `t`. Counting only since the unlock means that a key typed often in reading Passages before its unlock still gets its Introduction Drills.
  - While they are due, every Drill is made by the `introduction` generator. Drills use only the Unlocked keys (stored as a JSON list in `drill.unlocked`) until all are unlocked. The Introduction Drills of the last key to unlock use them too. After that `drill.unlocked` is NULL again. The word pool is now filtered before the `SMALL_POOL` check, so the built-in word list joins a pool that the Unlocked keys made small.
  - The page asks for a Drill with `{"introduction": true}` when it expects an Introduction Drill after an Attempt. If none is due any more, the server makes no Drill and the page goes back to the Passage. A finished or skipped Passage moves its Source on after the Introduction Drills.
  - `GET /api/sessions/{session}/keymap`, the Attempt summary, the Drill response and the progress page return `unlocking`: `{unlocked, total, next, introducing}`, or null for other Letter layouts. The page fetches the keymap drawings again when `unlocked` changes.
- #31 added Python Lessons, without code checking (#32 adds it).
  - Lesson requests wait in an `asyncio.Queue` inside `create_app`. One task, started with the app, writes them one at a time in the order asked for. Each ends with a notice: ready, or failed and why. A failure does not stop the task. Requests in the queue are lost when the server stops.
  - `create_app` takes a `Provider` (`lessons.py`): `prices(model)` (dollars per prompt and per output token) and `write(model, messages, max_tokens, reasoning) -> Reply(text, usage, dollars)`. `main()` gives it `OpenRouter(Path(".env"))`, which reads the key for each call and the price list once per server run (`GET /api/v1/models`, no key); a model added to OpenRouter later needs a restart. Tests give a fake provider, so they never use the network. A provider for another company only needs these two methods.
  - The new table `lesson` records each Lesson that the model wrote: time, topic (also the Source's title), language, model ID, prompt name, the `[lessons]` settings as JSON, the raw output, and its Source (NULL when it had nothing to type). The Source's text is the same raw output. A call that fails gets no row.
  - The new table `spend` is the ledger: one row per call to a model, with its Lesson, time (UTC), the usage JSON as the provider gave it, and the cost in dollars as charged. Month-to-date spend = the dollars since the start of the calendar month in UK time ÷ `dollars_per_pound`. Before a request is queued, its worst case (a token for each character of the prompt, plus `max_tokens` output tokens) and the worst cases of the requests still in the queue (`waiting`, in memory) are added; if that is more than `cap`, it is refused with "Cap reached: resets 1 Nov" (409) and nothing is sent. The provider's own spend limit (about $6.70) stops any larger overspend. #32 should add the repair calls to the worst case and write a `spend` row for each of them.
  - `passage.heading` (new column, NULL for other Sources) is the Lesson heading above a Passage. The server sends it with each served Passage, and the page shows it above the Passage. It is not typed.
  - `sources.lesson_passages` splits the Markdown: each paragraph and list item is a prose Passage without inline markup; each code block is a code Passage, split at blank lines before unindented lines when over `split_lines` (40); tables are dropped and count as skipped. Inline code needs no style of its own, because the whole Passage is in a monospace font.
  - The `[lessons]` settings: `prompt`, `python_model` (#33 adds a model for Gleam the same way), `reasoning`, `max_tokens`, `words`, `level`, `split_lines`, `cap` and `dollars_per_pound`.
- #32 added the check of a Lesson's code.
  - `lessons.run_code(language, code, timeout)` writes the block into a new temp folder, with the function `RUNNERS[language]`, and runs the command that it gives under `sandbox-exec` with the profile `SANDBOX`: no network, writes only in that folder (and `/dev/null`). TMPDIR is that folder. The block passes when it ends with exit code 0 within `timeout` seconds. Its output is thrown away; the last 2,000 characters of its error output are kept. Its whole process group is killed at the end. Python blocks run with the server's own Python (`sys.executable -I -S`), so only the standard library can be imported. #33 adds a Gleam function to `RUNNERS`; it can copy a pre-made project into the folder and give `gleam run`.
  - `write_lesson` runs each fenced code block of the model's Markdown (`sources.CODE_BLOCK`, the same fence rule as `lesson_passages`), one at a time, in a thread. A failing block is sent to the model with its error (`LessonPrompt.repair`), up to `repairs` times, each answer at most `repair_tokens` tokens; the code of the first fenced block in the answer replaces it. Then it is dropped. Each repair call has its own `spend` row with the Lesson's id.
  - When more than `drop_share` of the blocks are dropped, or none is left, the same prompt is sent once again (`lessons.WRITES = 2`), and then the Lesson is rejected. Each time it is written has its own `lesson` row; one that failed the check has `source` NULL.
  - New column `lesson.checks`: JSON, for each code block a list of its checks `{code, error}`, error NULL when it passed. The Source's text is the checked Markdown (repaired blocks in, dropped blocks out); `lesson.output` keeps the raw output.
  - `LESSON_PROMPTS[name]` is now a `LessonPrompt(write, repair, blocks)`: the prompt name covers the repair prompt too, and `blocks` is the most code blocks that the prompt asks for (6).
  - The worst case at `POST /api/lessons` (`lessons.worst_case`) is now the Lesson written twice, each time with `repairs` repair calls for each of the prompt's `blocks` blocks. A repair prompt is counted with a block of `repair_tokens` characters and 2,000 characters of error. A Lesson with more blocks than that can go a little over the cap, as the spec allows.
