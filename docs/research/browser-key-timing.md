# What key timing can the browser actually observe?

Resolves issue #3 (part of map #1). Researched 2026-10-25.

**Question.** With QMK/Vial boards (mod-taps, layer-taps, combos, Caps Word, macros), what does the browser's keyboard
event stream really show, how precise are `event.timeStamp` / `performance.now()` in Chrome, Safari and Firefox, and
therefore what can and cannot be measured about real finger timing?

**Keyboard configuration assumed** (from `sweep-layouts/README.md`, "QMK settings"): tapping term 200 ms, permissive
hold on, hold-on-other-key-press off, retro tapping off, quick tap term 120 ms, chordal hold off, flow tap off, combo
term 40 ms; bottom-row mod-taps and thumb layer-taps.

## Short answer

1. The host never sees a physical key press for a tap-hold key. QMK holds the press back until it has decided tap or
   hold. A **tap** reaches the host as press and release back to back **at the moment the finger lifts**. A **hold**
   reaches the host as a modifier press at the **decision time** (not the finger-down time), or as no event at all for a
   layer-tap, because a layer switch is internal to the keyboard.
2. Keys that merely sit in the same buffer as a pending decision (the key typed while a mod-tap is undecided, or any key
   that is part of a combo) are held back and replayed late, with their down and up collapsed together.
3. Macros, Caps Word's shift, combo outputs and auto-repeat are generated by firmware or the OS, not by a finger.
4. The USB HID report carries no timestamp, so the host stamps events when it receives them. The clocks are good
   (about 0.1 ms to 1 ms depending on the browser) but the USB frame (1 ms) and debounce (5 ms default) dominate the
   timing noise, and both are small next to typing intervals of tens to hundreds of ms.
5. So: browser clocks are not the problem. **Firmware tap-hold and combo logic is the problem**, and it biases specific,
   identifiable keys. It is correctable if the analysis knows the Keymap (ticket #2) and models those keys explicitly.

Everything below is the evidence. Source versions are noted where they matter. Claims marked **(inference)** follow
from the cited code but were not confirmed by an experiment on the actual hardware. See "Open questions".

---

## 1. What the keyboard sends: the HID report

- The keyboard sends HID reports that contain only the *state* of the keys: modifier bits, a reserved byte, and up to 6
  keycodes (boot-style), or a bitmap (NKRO). There is no timestamp field.
  [QMK `report.h`](https://github.com/qmk/qmk_firmware/blob/master/tmk_core/protocol/report.h) (`report_keyboard_t`,
  `report_nkro_t`).
- Consequences (inference): the OS timestamps a key event when it receives the report. If two key changes are in the
  same report, they have the same host time. The browser's `event.code` reflects the **keycode the firmware sent**, not
  the physical switch position, so recovering physical position needs the Keymap from the `.vil`.
- The interrupt endpoint is polled by the host. QMK's default polling interval is 1 ms
  (`#define USB_POLLING_INTERVAL_MS 1` in
  [`usb_descriptor.c`](https://github.com/qmk/qmk_firmware/blob/master/tmk_core/protocol/usb_descriptor.c); the config
  docs' example value of 10 is just an example,
  [`config_options.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/config_options.md)). For a full-speed
  device, `bInterval = 1` means a 1 ms frame
  ([Microsoft: USB_ENDPOINT_DESCRIPTOR](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbspec/ns-usbspec-_usb_endpoint_descriptor)).
  So report arrival is quantised to about 1 ms. Boards can override this, and a board with 8 ms polling would add up to
  8 ms of jitter.
- Reports are sent one at a time and the next waits for the endpoint to be free (ChibiOS: `usb_endpoint_in_send` with a
  100 ms timeout in
  [`usb_main.c`](https://github.com/qmk/qmk_firmware/blob/master/tmk_core/protocol/chibios/usb_main.c)). Two reports
  produced in the same matrix scan therefore arrive in consecutive polls, about 1 ms apart **(inference)**.
- Firmware-side timing: QMK stamps each key event with `timer_read()` (1 ms, 16-bit) when the event is generated
  ([`keyboard.h`, `MAKE_EVENT`](https://github.com/qmk/qmk_firmware/blob/master/quantum/keyboard.h)), i.e. after the
  matrix scan and debounce. Default `DEBOUNCE` is 5 ms with the `sym_defer_g` algorithm: "wait for no changes for
  DEBOUNCE ms before reporting change", so every press and release is reported about 5 ms late, symmetrically
  ([`config_options.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/config_options.md),
  [`feature_debounce_type.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/feature_debounce_type.md)). A
  constant offset like this cancels in dwell and flight differences. The per-board debounce setting is not in the
  layout README, so it is unknown.

## 2. Tap-hold keys (mod-taps and layer-taps)

Sources: QMK [`quantum/action_tapping.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/action_tapping.c),
[`quantum/action.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/action.c) and
[`docs/tap_hold.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/tap_hold.md), read from `master`. The Vial
fork's [`action_tapping.c`](https://github.com/vial-kb/vial-qmk/blob/vial/quantum/action_tapping.c) has the same state
machine (same `waiting_buffer_scan_tap`, "Tapping: End. Timeout. Not tap(0)" and so on). Vial exposes the settings as its
"QMK Settings" tab
([`qmk_settings.c`](https://github.com/vial-kb/vial-qmk/blob/vial/quantum/qmk_settings.c)).

### 2.1 The press is withheld

The docs say it directly: "until the tap-or-hold decision completes (which happens when either the dual-role key is
released, or the tapping term has expired, or the extra condition for the selected decision mode is satisfied), key
events are delayed and not transmitted to the host immediately" (`tap_hold.md`, "Tap-Or-Hold Decision Modes"). Mod-taps
"do not send the modifier until the tap-hold decision is finalized" (same file, Speculative Hold section, which is a
newer opt-in feature not enabled in your settings).

In `process_tapping()`, a pressed tap-hold key in the idle state becomes `tapping_key` and the function returns without
calling `process_record` (no output): the branch `else if (event.pressed && is_tap_record(keyp))` sets
`tapping_key = *keyp;` and nothing is sent. Every later event is parked in `waiting_buffer` (`waiting_buffer_enq`)
until the decision.

### 2.2 The four outcomes and what the host sees

| Outcome | Trigger (code path in `process_tapping`) | What reaches the host |
| --- | --- | --- |
| **Tap** | Key released within tapping term, nothing else pressed: `tapping_key.tap.count = 1; process_record(&tapping_key);` ("Tapping: First tap(0->1)"), then the release is processed straight after. | `register_code` (key down) then `unregister_code` (key up) in the same scan, at the time of the **physical release**. Gap between them is `wait_ms(TAP_CODE_DELAY)`, default 0 (`action.c`, MODS_TAP and LAYER_TAP "Tap: unregister_code"; `TAP_CODE_DELAY` defaults to 0 in `action.h`). Vial makes this a runtime setting, `tap_code_delay` (`qmk_settings.c`), whose value for your boards is not in the README. |
| **Hold by timeout** | Another event arrives or a tick occurs after the tapping term with `tap.count == 0`: "Tapping: End. Timeout. Not tap(0)" then `process_record(&tapping_key)`. | Mod-tap: modifier down at **press + 200 ms** (strictly: at the first event or 1 kHz tick after the term). Layer-tap: nothing, the layer just turns on. |
| **Hold by permissive hold** | Another key is **pressed and released** while the tap-hold key is down: the `else if (!event.pressed && waiting_buffer_typed(event) && TAP_GET_PERMISSIVE_HOLD ...)` branch, "Tapping: End. No tap. Interfered by typing key", `process_record(&tapping_key)`. | Mod down (or layer on) at the **release of the nested key**, then the buffered press and release of the nested key are replayed immediately. The nested key's press and release arrive together. |
| **Rolling press stays a tap** | Tap-hold key released while another key is pressed but not yet released: `waiting_buffer_scan_tap()` finds the release and settles as a tap ("Rolling presses still count as taps", `tap_hold.md`, Permissive Hold). | Tap key down+up at its own release, then the later key's press (replayed from the buffer right after). |

Because the permissive-hold decision fires on the nested key's *release* event, the nested key's own press is only
replayed at that point, so the browser's key-down for it carries (about) its **release** time **(inference from the
code path above)**. One exception: the release of a key that was already pressed *before* the tap-hold key started is
processed immediately ("Release of key should be process immediately", `process_tapping`), so such releases are not
delayed.

`event.time` inside QMK is the real matrix-event time, and `WITHIN_TAPPING_TERM` is computed from those, not from when
the buffer drains. So the firmware decides correctly; the *host* just receives the result late.

### 2.3 Layer-taps in particular

`ACT_LAYER_TAP` with `tap_count == 0` does `layer_on()` on press and `layer_off()` on release (`action.c`). Neither
generates a HID report. The browser sees **nothing** for a held Space-as-SYM thumb: no keydown, no keyup, no
modifier. Only the keys typed on the layer, with their output keycodes, are visible. The hold duration of a thumb
layer-tap is unobservable except as a lower bound (the layer was active from decision time to the last layer key).

### 2.4 Quick tap term (the one case where the press *is* immediate)

If the key is pressed again within `QUICK_TAP_TERM` (120 ms) of the previous press and the first tap was not
interrupted, the second press is processed immediately as a tap: `Tapping: Tap press(n)` followed by
`process_record(keyp)` with `tap.count += 1` (the `WITHIN_QUICK_TAP_TERM` branch). The host sees a key-down at the
physical press, and then the OS auto-repeats it ("`a` will be sent on the first release, then `a` will be sent on the
second press, allowing the computer to trigger its auto repeat function", `tap_hold.md`, Quick Tap Term). The window runs
from the previous **release** to the new press: after a tap release the code does `tapping_key = *keyp;` (the release
event), and `WITHIN_QUICK_TAP_TERM` is `TIMER_DIFF_16(e.time, tapping_key.event.time) < QUICK_TAP_TERM`. This matches the
docs: "the timing between `SFT_T(KC_A)` up and `SFT_T(KC_A)` down must be within `QUICK_TAP_TERM`".

### 2.5 Failure mode worth logging

With retro tapping off (your setting), a tap-hold key held longer than 200 ms with no other key pressed outputs
**nothing** for a mod-tap (`tap_hold.md`, Retro Tapping: "Without this option, releasing a dual-role key with no other
key pressed sends nothing"). A Passage character that was meant to be typed by a slow tap of a bottom-row mod-tap will
simply never arrive. That is a firmware-induced "omission", not a finger error.

## 3. Combos

Sources: [`process_combo.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/process_keycode/process_combo.c)
(Vial's copy is structurally the same,
[vial-qmk](https://github.com/vial-kb/vial-qmk/blob/vial/quantum/process_keycode/process_combo.c)),
[`docs/features/combo.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/features/combo.md).

- Any key that is part of **any** combo is buffered when pressed: `key_buffer[key_buffer_size++] = ...` and
  `timer = timer_read()` (the timer restarts at each combo-key press unless `COMBO_STRICT_TIMER`, "Normally, the timer
  is started on the first key press and then reset on every subsequent key press within the COMBO_TERM",
  `combo.md`).
- If no combo completes, `combo_task()` flushes the buffer once `timer_elapsed(timer) > longest_term`
  (`dump_key_buffer()`), or a non-combo key or a release flushes it earlier (the `else` branch of `process_combo`).
  Flushed records are replayed with their **original `event.time`** (so tap-hold logic still sees the true press time),
  but the host receives them at flush time. Net effect for a key that belongs to a combo but is typed alone: the host
  sees its key-down up to **40 ms late**, or, if the finger releases first, its down and up arrive together at the
  release, so dwell reads as about 0.
- A completed combo is queued "so we can fire it after COMBO_TERM" (comment in `process_single_combo`) or earlier if a
  release arrives, then emitted as one synthetic key event (`record->event.type = COMBO_EVENT`, `record->keycode =
  combo->keycode`), and the constituent keys become ticks. The combo's key-up is generated when the *last* constituent
  is released (`release_combo` in the "last key released" branch). There is no per-finger information in that output.
- Combos with `COMBO_MUST_HOLD`/`MUST_TAP` variants wait longer (`_get_wait_time`, `COMBO_HOLD_TERM`). The README does not
  say these are used.

## 4. Caps Word

Sources: [`process_caps_word.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/process_keycode/process_caps_word.c),
[`caps_word.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/caps_word.c),
[`docs/features/caps_word.md`](https://github.com/qmk/qmk_firmware/blob/master/docs/features/caps_word.md).

- The toggle keycode is consumed in firmware (`if (keycode == QK_CAPS_WORD_TOGGLE) { if (record->event.pressed)
  caps_word_toggle(); } return false;`). The host sees no event for entering or leaving Caps Word. (If Caps Word is
  triggered by a combo, you see nothing from it either.)
- While on, letters get a **weak** Left Shift (`add_weak_mods(MOD_BIT(KC_LSFT))`) and `send_keyboard_report()` is called,
  so the HID report contains Shift plus the letter. Weak mods are cleared when the next key is pressed
  (`action_exec`: "clear the potential weak mods left by previously pressed keys"). Browsers will therefore see Shift
  state/events that are not caused by a Shift keypress and whose timing follows the letter, not a finger **(inference
  about exact event shape on each OS: not tested)**.
- It times out after 5 s idle by default (`CAPS_WORD_IDLE_TIMEOUT`), silently.

## 5. Macros

- Vial macros are played by `dynamic_keymap_macro_send()` in
  [`dynamic_keymap.c`](https://github.com/vial-kb/vial-qmk/blob/vial/quantum/dynamic_keymap.c): a loop of `send_string`
  for tap/down/up and an explicit wait for delay items. Vial taps use `vial_keycode_down()`, `qs_wait_ms(QS_tap_code_delay)`,
  `vial_keycode_up()`
  ([`vial.c`](https://github.com/vial-kb/vial-qmk/blob/vial/quantum/vial.c)). QMK's `send_string` uses
  `TAP_CODE_DELAY` (default 0) between actions
  ([`send_string.c`](https://github.com/qmk/qmk_firmware/blob/master/quantum/send_string/send_string.c)).
- So a macro produces a burst of key events paced by the firmware and the USB poll (about 1 ms apart if
  `tap_code_delay` is 0), with timing unrelated to any finger. The key that triggered the macro generates no HID
  event of its own **(inference)**.

## 6. Auto-repeat

- The keyboard sends one down and one up. Repeats are generated by the OS (QMK docs: "allowing the computer to trigger
  its auto repeat function", `tap_hold.md`). UI Events requires the browser to mark them: "Holding down a key MUST
  result in the repeating the events keydown, beforeinput, input in this order, at a rate determined by the system
  configuration" ([UI Events](https://w3c.github.io/uievents/)), and `KeyboardEvent.repeat` is "true if the given key
  is being held down such that it is automatically repeating"
  ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/repeat)).
- Chrome on macOS sets the auto-repeat flag from `NSEvent.ARepeat`
  ([`web_input_event_builders_mac.mm`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/input/web_input_event_builders_mac.mm):
  `modifiers |= blink::WebInputEvent::kIsAutoRepeat`).
- Repeat events have OS-clock spacing, not finger meaning. A held key's dwell time is the first `keydown`
  (`repeat === false`) to `keyup`.

## 7. What the browser reports about time

### 7.1 Specs

- DOM Standard: `Event.timeStamp` is initialised to "the relative high resolution coarse time given *time* and event's
  relevant global object", where *time* is "the time of the occurrence that the event is signaling", with the note
  "In macOS the time of the occurrence for input actions is available via the `timestamp` property of NSEvent objects"
  ([DOM, create an event / inner event creation steps](https://dom.spec.whatwg.org/#concept-event-create)). So the
  spec intends **event occurrence time**, not the time the JS handler ran. (MDN's wording "the time at which the event was
  created" is looser,
  [MDN `Event.timeStamp`](https://developer.mozilla.org/en-US/docs/Web/API/Event/timeStamp).)
- High Resolution Time: the coarsen-time algorithm sets "time resolution" to **100 microseconds**, or 5 microseconds
  if the cross-origin isolated capability is true, "or a higher implementation-defined value", and allows jitter
  ([HR-Time, "coarsen time"](https://w3c.github.io/hr-time/#dfn-coarsen-time)). The clock is monotonic and not subject
  to system clock adjustments, and exists only within one browser run.
- Cross-origin isolation = response headers `Cross-Origin-Opener-Policy: same-origin` plus
  `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`); it makes `performance.now()` more precise
  ([MDN `crossOriginIsolated`](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated)). A local
  Python server can send those headers.
- `event.timeStamp` and `performance.now()` share the same time origin, so `performance.now() - event.timeStamp`, read in
  the handler, estimates how long the event waited on the main thread **(inference)**. That makes a cheap health check
  for dropped or delayed handlers.

### 7.2 Per browser (verified against engine source on 2026-10-25, plus MDN's table)

MDN summary: "In Chrome, the rounding interval is 0.1 ms, or 0.005 ms in cross-origin-isolated contexts. In Safari, it is
1 ms, or 0.02 ms in cross-origin-isolated contexts. In Firefox, the `privacy.reduceTimerPrecision` preference is enabled
by default and uses a rounding interval of 1 ms, or 0.02 ms in cross-origin-isolated contexts. If
`privacy.resistFingerprinting` is enabled, the rounding interval is 16.667 ms" ([MDN `Event.timeStamp`](https://developer.mozilla.org/en-US/docs/Web/API/Event/timeStamp)).
The engine sources agree:

Platform caveat for Chrome (matters if you ever type on Windows): `EventTimeFromMSG` deliberately **ignores** the
OS message timestamp and uses `TimeTicks::Now()` at the time the message is processed, because the OS value
comes from `GetTickCount()` with a different origin
([`events_win_utils.cc`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/events/win/events_win_utils.cc)).
So on Windows Chrome the timestamp is when the browser process handled the message, which includes any browser-process
queueing delay, not when the OS received the key. On macOS all three browsers use the AppKit event timestamp.

What AppKit's `NSEvent.timestamp` represents (when the HID event was received by the system, presumably) was not
verified: Apple's documentation page could not be retrieved in this research. **(unverified)**

### 7.3 What the numbers mean in practice

- Resolution floor in the browser: 0.1 ms (Chrome), 1 ms (Safari, Firefox), none of which matters against a 1 ms USB
  frame and a typical key interval of 80 ms to several hundred ms.
- Cross-origin isolation would improve Chrome to 5 us and Safari/Firefox to 20 us, but below ~1 ms the USB poll
  interval is the limit. It is not worth the COOP/COEP header risk (it breaks cross-origin embeds) unless a later feature
  wants it.
- Jitter (Chrome, Firefox) is a random threshold per interval, so individual stamps can shift by up to one resolution
  step. Over thousands of events this is noise, not bias.
- Safari/Firefox at 1 ms means any single interval has +/-1 ms quantisation error. Dwell times of 60-120 ms are fine.
  Tap-hold "dwell" of ~0 ms cannot be resolved finer than that, but doesn't need to be.

## 8. Putting it together: what is observable, per key type

| Key / mechanism | Down timestamp the browser sees | Up timestamp | Finger timing recoverable? |
| --- | --- | --- | --- |
| Plain letter or symbol, not in a combo | Physical press + debounce + <=1 ms | Physical release + same | Yes. Dwell and down-to-down to ~1-2 ms |
| Plain key that belongs to some combo | Press delayed 0-40 ms (flush at timer, or at release) | Physical release | Partly. Down is late by up to 40 ms; if released before the term, dwell is collapsed |
| Mod-tap, **tapped** | **Physical release** | Same scan, +`tap_code_delay` (default 0) | Release time only. Press time and dwell are hidden |
| Mod-tap, **held** | Press + 200 ms, or the nested key's release (permissive hold) | Physical release | Release only. Press is hidden; decision time is a function of the nested key |
| Layer-tap, **tapped** (e.g. Space) | Physical release | Same scan | As mod-tap tapped |
| Layer-tap, **held** | None | None | No direct signal; only lower bounds from layer keys |
| Key typed while a tap-hold key is undecided | Replayed at the decision (at its own release if decision is permissive hold) | Same instant | Release only; press and dwell collapsed |
| Combo output | After the last constituent press, up to 40 ms | Last constituent release | No per-finger timing |
| Macro output | Firmware-paced burst | Firmware-paced | None |
| Caps Word Shift | Tied to the next letter's report | Cleared at next press | None |
| Auto-repeat events | OS rate, `repeat === true` | n/a | None (use first non-repeat keydown to keyup) |
| Quick tap (tap-hold key re-pressed within 120 ms of its last release) | Immediate | Physical release | Yes |

## 9. Systematic biases the analysis must correct for

1. **Interval attribution shifts around tap-hold keys.** A tapped Space/thumb or bottom-row mod-tap is stamped at its
   *release*. The interval *into* it is overestimated by the finger's true dwell and the interval *out of it* is
   underestimated by the same amount. Total time is preserved, the split between the two neighbouring bigrams is not.
   Do not read per-bigram speed for any bigram that touches a tap-hold key; use the sum, or use release-based
   intervals.
2. **Rolls through tap-holds collapse.** In an A-down, B-down, A-up, B-up roll where A is a mod-tap, A's down and up
   are stamped at A-up, and B's down (replayed straight after) is within about 1 ms of it. True overlap and flight
   time are invisible; apparent flight is about 0-1 ms.
3. **Nested keys under permissive hold** get down = up = their own release. Their dwell and press time are lost, and
   any further keys pressed during the pending window are flushed in a burst at that release.
4. **Hold-decision latency.** Held mod-taps appear 200 ms after finger-down (timeout) or at a nested release. Never
   treat mod-down time as finger-down time.
5. **Combo constituents** are late by up to 40 ms and may lose dwell.
6. **Synthetic events** (macros, combo outputs, Caps Word shift, OS repeats) are not finger events and must be tagged
   and excluded from finger-timing statistics.
7. **Constant offsets** (debounce about 5 ms, scan time, 1 ms USB frame, OS stack) are the same for every key and cancel
   in differences between events of the same kind. They do not cancel between events with different pipelines (for
   example a plain key against a macro).
8. **Quantisation**: 1 ms (USB frame, Safari/Firefox) with extra jitter in Chrome and Firefox. Treat values below
   about 2 ms as zero.
9. **Layout dependence.** Everything above is specific to the Keymap and QMK settings. A change to tapping term,
   permissive hold, flow tap, combo term or `tap_code_delay` changes the biases; chordal hold or flow tap would add new
   cases (a tap-hold key "settled as tapped" earlier).
10. **Firmware-induced omissions**: a mod-tap or layer-tap Space held past 200 ms without another key outputs nothing
    (retro tapping off); a held layer-tap can turn a key into the wrong layer's character. These look like typing
    errors but are not.
11. **Windows Chrome** timestamps include browser-process queueing; macOS ones do not.
12. **Wired vs wireless.** The USB analysis assumes a wired board. A Bluetooth or ZMK board (the README mentions a
    Forager built from ZMK) has a different transport (connection intervals) and different tap-hold code. Not researched
    here.

## 10. Open questions (not answerable from documentation alone)

- Exact behaviour of `NSEvent.timestamp` for external USB keyboards on macOS: report arrival time or something
  coarser/derived? Needs a measurement (for example comparing against a known-rate synthetic key source).
- Your boards' real `DEBOUNCE`, `DEBOUNCE_TYPE`, `USB_POLLING_INTERVAL_MS` and `tap_code_delay`. All are readable from
  the firmware config or Vial's QMK Settings tab.
- Whether the browser sees Caps Word's Shift as discrete Shift keydown/keyup events or only as `shiftKey` state on the
  letter, per OS.
- Which combos exist in the `.vil` and which letters they cover (that decides how many ordinary keys carry the
  up-to-40 ms delay).
- Empirical dwell of tapped tap-hold keys (a direct measurement of `tap_code_delay` plus USB spacing: expect 0-2 ms).

A cheap calibration experiment answers most of these: record a session of mixed plain, tap-hold, combo and macro
keys with a simple page that logs `keydown`/`keyup`, `event.timeStamp`, `performance.now()` and `repeat`, and look at
the distribution of dwell and inter-event gaps by key class.

## 11. Calibration on real hardware (ticket #12, 2026-10-25)

Recorded with the throwaway page in [`key-calibration/`](key-calibration/) (`server.py`, `index.html`; summary in
`analyse.py`; raw logs in `key-calibration/logs/`). One Board, the **Cheapino v2 running the QWERTY keymap**
(`sweep-layouts/vil/cheapino.vil`, same QMK settings as every other Board), wired, on macOS, one run each in **Chrome
155** and **Firefox**: about 1,200 and 1,050 key events across 17 scripted steps. The Sweep, Sofle and Q3 Max were
dropped: the event shapes come from the firmware and its settings, which all Boards share, and the free-range Boards
would have meant hunting for keys.

### Confirmed

| Prediction | Observed (Chrome / Firefox) |
| --- | --- |
| Tapped mod-tap arrives as down+up at the physical release | Dwell median 0.3 / 0.0 ms; 97% / 83% under 2 ms (the rest are quick taps, below) |
| Tapped layer-tap (Space, Esc, Tab) likewise | Dwell median 0.4 / 0.0 ms; 99% / 91% under 2 ms |
| Quick tap term: re-tap within 120 ms is immediate | Firefox run re-tapped each mod-tap ~100 ms after the first: second tap kept a real 35-80 ms dwell |
| Held mod-tap alone: modifier down, nothing typed on release | Shift down, Shift up at release, no letter (retro tapping off) |
| Held layer-tap invisible | No event for the held Space; SYM keys arrive with their own codes |
| Combo constituents typed alone lose up to 40 ms of dwell | J/K/L dwell median 34 / 44 ms against 86 / 83 ms for other plain keys (L alone: 30 / 36 ms) |
| Combo output is one key event, constituents invisible | J+K, J+L, K+L gave one Escape / Enter / Backspace each, with a 40-90 ms dwell to the last release |
| Shifted keycodes wrap the key in a synthetic Shift | ShiftLeft down 0.3-1.8 ms before the key, up 0.2-0.8 ms after its up, for the key's full dwell |
| Caps Word: no event for the toggle, Shift tied to the letters | ShiftLeft down < 1 ms before the first letter, held across the word, up < 1 ms before Space; times out after 5 s idle |
| Shift + `_` override gives `-` with a Shift flicker | Shift up, `Minus` down (`-`, no Shift), then at the trigger's release Shift down, `Minus` up |
| Browser clocks | Chrome 0.1 ms steps; Firefox whole ms. Handler lag (`now - timeStamp`) median 3-4 ms, p95 ~15 ms, max 67 ms: irrelevant because `timeStamp` is used |
| Auto-repeat marked `repeat` | Chrome: first repeat 500 ms after the press, then every ~34 ms |

### Different from the predictions

1. **Firefox drops the key-up of a key pressed while Cmd is held.** All 4 Cmd+A chords in Firefox had no `KeyA`
   keyup, and a 2.6 s hold produced no repeat events either. Chrome delivered every keyup (and repeats). The recorder
   must close key-downs that never get a key-up (for example at the modifier's release) and flag them, and Chrome is
   the better browser for practice.
2. **A key-up's `key` can differ from its key-down's.** The override sends `Minus` down as `-` and up as `_`; rolling
   two shifted symbols (`}` then `?`) shared one synthetic Shift, so `?` went down as `?` and came up as `/` after the
   first key released it. Pair down and up by `code`, take the character from the key-down, never match on `key`.
3. **Macros are ~1 ms per event, not ~10 ms.** `->` and `|>` arrive as 6-8 events within about 3 ms in total (0 ms
   at Firefox's resolution): `tap_code_delay` (setting 18) is not set in the `.vil`, so it is 0. Macro detection by
   timing: a burst of events a few ms apart from no preceding press. `|>` typed `|>` on macOS, as expected.
4. Twice in Chrome a held Shift mod-tap's modifier arrived < 1 ms before the nested key's down, with the nested key
   keeping its full dwell: the tap-hold timeout settled on that key's press. Either way the modifier's down is not the
   finger's down, as predicted.

### Not tested

- **Permissive hold** (a key tapped inside a mod-tap's 200 ms term, which should arrive with down = up): every nested
  hold was held past the tapping term first, so all were timeouts.
- **Rolls off a tap-hold key** (next key down < 2 ms after a collapsed tap): typing on the Cheapino was steady, with
  almost no overlap (6 of 530 key-downs in Chrome, 53 of 468 in Firefox), and none touched a tap-hold key.
- Quick-tap auto-repeat on Space, `-` under Caps Word, plain-key auto-repeat in Firefox.
- The Q3 Max (`|>` probably typing `~>` under UK Windows), Windows browsers, wireless Boards, Safari.
- Debounce and USB polling: not looked up. They are constant per event and cancel in dwell and flight.

None of these change the design: raw events are stored and keys are classified from the Keymap, so these cases can
be checked from real practice data later.

## Implications for typokiller

1. **Record raw, process later.** Store every `keydown`/`keyup` with `event.timeStamp` (not `performance.now()` at
   handler time), `event.code`, `event.key`, `event.repeat`, `event.isComposing`, modifier state, plus
   `performance.now() - event.timeStamp` as a handler-lag health metric. Keep it all; interpretation depends on the
   Keymap and the QMK settings, both of which may change (feeds ticket #6, data model).
2. **Do not use cross-origin isolation, and do not worry about browser choice.** Browser clock resolution (0.1 ms
   Chrome, 1 ms Safari and Firefox) is below the 1 ms USB floor. Prefer `event.timeStamp` and keep one browser per
   Board for consistency. On Windows, prefer not to use Chrome for timing studies, or log which OS and browser.
   *Calibration (section 11):* browser choice does matter for one thing: Firefox on macOS drops key-ups under Cmd.
   Prefer Chrome, and pair key-downs with key-ups by `code`, tolerating a missing key-up.
3. **Classify every physical key from the Keymap** (ticket #2 supplies the `.vil` import): plain, mod-tap, layer-tap,
   combo constituent, combo output, macro output. Tag each stored event with its class and the Board's QMK settings
   (tapping term, permissive hold, combo term, quick tap term, `tap_code_delay`, debounce) so analysis can apply the
   right correction. Because the browser reports output keycodes rather than switch positions, mapping events to
   fingers/keys needs both the Letter layout and the layers.
4. **Define metrics by what is trustworthy:**
   - Use **down-to-down and up-to-down (flight)** only where both events are plain keys.
   - For anything involving a tap-hold key, use the **release time** (the browser's down for a tapped tap-hold key) and
     only report **sums** over neighbouring bigrams, or intervals measured from release to next press.
   - Never report dwell for tap-hold keys, combo constituents or macro outputs. Report dwell only for plain keys.
   - Treat Space (tap-hold on the thumb) as a release-time marker. Word-boundary pause measurement is fine, per-key
     speed of Space is not.
5. **Exclude or separately label synthetic events.** Drop `repeat === true`, bursts that match macro signatures
   (known macro output sequences, gaps of about 0-2 ms), and Caps Word shift when computing finger timing. Detect
   combos and macros by comparing the typed text with the Passage and the Keymap's combo/macro tables rather than from
   timing alone.
6. **Separate firmware errors from finger errors.** Flag: expected character absent where the key is a tap-hold held
   past the tapping term; wrong-layer character after a thumb hold; combo misfires. These feed the "feed back into
   keyboard design" goal (tapping term, combo term and key placement), not the finger-weakness model for Drills.
7. **Be careful with Drills built on bigram speed.** Bigram targeting from timing is valid for plain-plain pairs.
   Bigrams touching mod-tap or thumb keys should be scored by combined time over the neighbouring pair, or not at
   all, until a model of tap-hold effects has been validated.
8. **Make the settings part of the data.** If the Board's tapping term or combo term is changed in Vial, old data has
   different biases; record the settings in the Session (or Board revision) so analyses can stratify.
9. **First build task: a calibration page.** *(Done for the Cheapino: section 11.)* Before trusting any statistic, record a Session on each Board with
   deliberately varied keys and check the key-class dwell and gap distributions against the model in this note
   (answers section 10, and tells you the real `tap_code_delay`, debounce and polling effects).
